# Binding crdt.el and Yjs through one hub

Nobody has published a system that binds two different edge CRDTs through one hub replica, so the M-arxana-together design is new in that respect. Almost every piece it needs, though, has prior art. Server-relayed CRDT editing (crdt.el's own star topology, Jupyter RTC's server-side Yjs replica), event-graph logs that start centralised and decentralise later (Eg-walker, Weidner's server reconciliation), id-anchored spans (Peritext, Yjs relative positions) and tree move (Kleppmann et al. 2021) are all published and implemented. The research turned up three hard facts the mission does not yet account for. First, crdt.el turns any change to a synced text property into a delete plus a re-insert with fresh ids, so its text properties are a poor carrier for provenance that can change after insertion. Second, there is no maintained JVM binding for Yjs: the hub needs a sidecar, its own FFI binding to the Rust `yrs` library, or embedded JavaScript. Third, a log replayed later under a hub-less CRDT can order concurrent inserts differently from what users saw, unless each log entry records the hub's resolved placement. Two things are open: a cycle-safe move or regroup for a hypergraph, and a convergence proof for one process taking part in two different sequence CRDTs. The notes also surfaced a simpler architecture, one merge engine at the hub with thin editor clients (Ethersync/Teamtype, braid-text). It removes the cross-CRDT tie-order and id-mapping problems, but gives up crdt.el's and Yjs's existing peer sync and editor bindings.

**How claims are marked.** Sourced claims carry an inline link. Claims the research notes reached by reasoning, with no source behind them, are marked *(researchers' inference)*. Claims this report adds by putting the notes together are marked *(report inference)*. Where the researchers checked something by running code (crdt.el 0.3.5 in batch Emacs, driven from a raw Python TCP client on 2026-11-20), the claim is marked *(researchers' local experiment)*, and the link points to the source it was checked against.

## Design points 1–3: the hub can bind both CRDTs, but only with an atomic replay step

### What crdt.el's server already does, and why the hub should take that role

crdt.el (the mission says "version 0.3.0"; that is the **protocol** string, and the last release is **0.3.5, 2024-03-31**) implements **Logoot-split** (André et al., CollaborateCom 2013). It runs as a **star**: one Emacs is the server, which applies each client's op to its own buffer and then relays the original message bytes, unchanged, to every other client. The server does not transform, reorder or acknowledge anything ([crdt-0.3.5 source](https://elpa.gnu.org/packages/crdt-0.3.5.tar); [HACKING.org](https://code.librehq.com/willforan/crdt.el/-/raw/38476dac4630b18bbf3199ee6ab26a9e95c96fc0/HACKING.org)). The researchers recommend that the hub take the **server** role, so that Emacs users `crdt-connect` to it. As a crdt.el *client*, the hub would also have to serve blocking RPCs started by the server and the `var` diff semantics *(researchers' inference)*. The researchers tested this: a non-Emacs Python client joined a crdt.el server, passed the password challenge, obtained write access through the RPC, and inserted non-ASCII text *(researchers' local experiment)*. So a non-Emacs program can take part in a session, and the protocol can be spoken from outside Emacs.

crdt.el's convergence rests on two things: globally unique Logoot ids, and the in-order delivery that the TCP star gives. There is no version vector, acknowledgement or causal check. When an op fails to apply, the client recovers by re-fetching the whole buffer (`get`) ([crdt-0.3.5 source](https://elpa.gnu.org/packages/crdt-0.3.5.tar)). So a hub acting as crdt.el server must **keep each buffer's messages in arrival order and must not reorder or batch-merge across clients** *(researchers' inference)*. The researchers also found two risks to id uniqueness. When the 16-bit site-id space runs out, the server takes a site id back from a live user without telling them (the source comment reads "todo: notify the victim"). And the block-extension check at line 1257 compares a *site* id with a *user* id; the researchers flagged this as a possible bug and did not reproduce it. The suggested mitigations are to never recycle site ids and to hand out site-id = user-id *(researchers' inference)*.

### What Yjs gives a server peer, and what the JVM lacks

The y-protocols wire format is small and fully specified: LEB128 varuints, message type 0 = sync and 1 = awareness, and sync sub-messages step1 (state vector), step2 (diff update) and update ([y-protocols PROTOCOL.md](https://github.com/yjs/y-protocols/blob/master/PROTOCOL.md)). Answering step1 with a correct diff, applying updates and reading the text all need a full Yjs-compatible CRDT engine. **No maintained JVM binding exists.** The y-crdt organisation lists bindings for Python, Ruby, R, .NET, Swift and Kotlin, and the Kotlin one (`ykt`) is marked inactive ([y-crdt/y-crdt](https://github.com/y-crdt/y-crdt); [y-crdt/ykt](https://github.com/y-crdt/ykt)). Yrs4J is an incomplete, GPL-2.0 JNA wrapper pinned to yrs 0.18.8 ([segreeeen/Yrs4J](https://github.com/segreeeen/Yrs4J)). XWiki, a large Java project, concluded in May 2026 that a server-side Y.Doc would be "the best by far, if only a Java implementation was available", and fell back to recording updates and replaying them ([XWiki forum](https://forum.xwiki.org/t/support-for-y-js-in-java/16908)). The routes left are these. One is a sidecar: **pycrdt 0.14.13** (2026-11-02, Project Jupyter's yrs binding, MIT), which the mission already names ([PyPI pycrdt](https://pypi.org/project/pycrdt/)), or a Node process running Hocuspocus. Another is Panama FFM or JNI bindings to `yffi`, the C FFI over **yrs 0.28.2** (2026-11-19, MIT) ([crates.io yrs](https://crates.io/api/v1/crates/yrs/versions)). The last is real Yjs in GraalJS. The researchers believe GraalJS now runs on stock OpenJDK, but they did not verify it *(researchers' inference)*. A relay that only merges update bytes (`mergeUpdates`, `diffUpdate`) can answer step1, but it cannot make edits or read the text, so it does not meet the hub requirement *(researchers' inference)*.

On the code-server side, the editor binding has to be written. y-monaco binds Monaco, but **there is no first-party Yjs binding for the VS Code extension API** ([y-monaco](https://github.com/yjs/y-monaco); [discuss.yjs.dev](https://discuss.yjs.dev/t/cannot-find-vscode-binding/1224)). Eclipse Open Collaboration Tools is the most mature open VS Code/Theia collaboration stack and has a Yjs integration package. Its host-owns-workspace model differs from a hub that holds the authoritative copy ([eclipse-oct](https://github.com/eclipse-oct/open-collaboration-tools)). The researchers suggest an extension running in code-server's server-side extension host, which maps `onDidChangeTextDocument` to Y.Text ops, applies remote deltas as `WorkspaceEdit`s with echo suppression, and shows authorship with decoration types *(researchers' inference)*.

### The convergence argument is assembled by the researchers, not published

The researchers found **no published system, paper or proof for one process taking part in two different sequence CRDTs**. The nearest working designs all bridge one CRDT to a non-CRDT edge. Ethersync/Teamtype runs an Automerge daemon with editors on a revision-counter OT protocol ([Teamtype docs](https://teamtype.github.io/teamtype/print.html)). braid-text runs a diamond-types server with history-free Simpleton clients ([braid-text](https://github.com/braid-org/braid-text)). Jupyter RTC overwrites a server-side pycrdt document when the file changes on disk ([jupyter-collaboration #243](https://www.github.com/jupyterlab/jupyter-collaboration/issues/243)). The closest formal tool is Liittschwager et al.'s treatment of CRDT emulation as weak simulation (ICFP 2025). It covers state-based versus op-based emulation, not two different sequence CRDTs ([arXiv 2504.05398](https://arxiv.org/abs/2504.05398)).

The researchers' argument *(researchers' inference)* is as follows. Handle each incoming op under one lock: integrate it into its native replica, compute the text delta from the hub's post-integration state, apply that delta to the other replica as a local edit tagged with a hub origin, and append one attributed log entry. The invariant is then `text(hub_crdt.el) == text(hub_Yjs)` whenever the hub is between steps. Each edge converges to its hub replica by its own CRDT's guarantee, so all edges converge on the same text. **Convergence holds; intention preservation does not.** When an Emacs user and a browser user insert at the same spot at the same moment, the final order is decided by hub arrival order and by one library's tie-break. Neither user can predict it, and a run typed on one side can arrive on the other split by the other user's characters. Interleaving is a property of the algorithm family. FugueMax is proven maximally non-interleaving ([Weidner & Kleppmann, arXiv 2305.00583](https://arxiv.org/abs/2305.00583)), and Eg-walker's authors conjecture the same for their Yjs-like variant ([arXiv 2409.14252](https://arxiv.org/html/2409.14252v1)). The notes did not confirm whether Logoot-split interleaves forward.

The researchers name these failure modes. **Echo loops** happen when a replay fires the other replica's observer and is forwarded back as a duplicate insert with a new identity. Yjs prevents this with transaction origins (`doc.transact(fn, origin)`; [Yjs docs](https://docs.yjs.dev/llms-full.txt)), and Teamtype states the same rule for its plugins ([Teamtype docs](https://teamtype.github.io/teamtype/print.html)). The notes did not confirm how crdt.el suppresses its own echo. **Position units** are a second risk: Yjs `Y.Text` length counts **UTF-16 code units** ([docs.yjs.dev Y.Text](https://docs.yjs.dev/api/shared-types/y.text)), Emacs counts characters, and Teamtype chose Unicode scalar counts, so mapping by integer index corrupts text after any emoji *(researchers' inference)*. A JVM hub that holds text as Java strings is also working in UTF-16 *(researchers' inference)*. **Whole-text overwrite** as replay is a third risk: Jupyter's out-of-band path grows the document by at least the file size per change, and it produced duplicated cells ([jupyter-collaboration #243](https://www.github.com/jupyterlab/jupyter-collaboration/issues/243); [jupyter-ydoc changelog](https://jupyter-ydoc.readthedocs.io/en/latest/changelog.html)). The fourth is a **hub restart** that rebuilds the two replicas from different snapshots and silently breaks the text-equality invariant; the researchers suggest checking equality on load *(researchers' inference)*.

The mission does not mention one more consequence. **Each crdt.el client is still a peer of the others through the crdt.el server, and each Yjs client of the others.** If the hub is the crdt.el server and the only Yjs server, every op passes through it and the argument above applies. If browsers also sync peer-to-peer (y-webrtc, for instance), the Yjs side has paths the hub does not order *(report inference)*. The researchers make the same point when contrasting the design with Teamtype, where the daemon is the only path *(researchers' inference)*.

## Design point 4 and the decentralisation requirements: the log is an Eg-walker event graph

### Ids and id-relative ops have direct published analogues

The mission's three requirements are editor-local ids (`murch:412`), operations that name ids ("insert after `joe:88`"), and per-entry causal parents. These are the event format of **Eg-walker**: each event is "uniquely identified by a pair of a replica ID and a per-replica sequence number" and carries the ids of its parent events, and a version is a frontier ([Gentle & Kleppmann, EuroSys 2025, arXiv 2409.14252](https://arxiv.org/html/2409.14252v1)). The paper states that "server-based OT corresponds to event graphs with one main branch representing the server's view", and proves that every topological order of the graph gives the same final document. So a hub-ordered log can later be merged with logs that grew without a hub. Weidner's "Collaborative Text Editing without CRDTs or OT" (2025-05-21) describes the same scheme from the server side: a unique id per character, insert-after-id ops, server receipt order as the truth, tombstones for deletes, rich-text ranges stored as id pairs. He shows that the decentralised variant "is a text-editing CRDT", close to Fugue ([mattweidner.com](https://mattweidner.com/2025/05/21/text-without-crdts.html)).

### The risk: native ids do not carry the author, and later replay can reorder ties

Every character the hub writes into the other side gets a *native* id owned by the hub. In Yjs that id is `{client, clock}`, and the `clientID` is a random uint32 per Doc ([yjs Doc.js](https://raw.githubusercontent.com/yjs/yjs/v13.6.33/src/utils/Doc.js)). In crdt.el it is a Logoot id built from the hub's site id. The original author therefore survives only in the hub log, and the hub needs a **two-way map from log id to crdt.el id and from log id to Yjs item id**. The map is updated in the same atomic step and grows with every inserted run *(researchers' inference)*. The researchers give Yjs a further option: give each logical writer its own clientID and map it to an identity with `PermanentUserData` ([PermanentUserData.js](https://raw.githubusercontent.com/yjs/yjs/v13.6.33/src/utils/PermanentUserData.js)). They add that reusing a clientID across concurrent Doc instances corrupts the document. That rule is well known, but they did not fetch a primary statement of it *(researchers' inference)*.

The researchers raise a semantic mismatch *(researchers' inference)*. During the hub era, concurrent same-position inserts are ordered by crdt.el's or Yjs's tie-break plus hub arrival order. A hub-less replay of the same graph under Eg-walker or FugueMax rules decides those ties its own way, so historical documents could replay differently from what users saw. They offer two fixes. The first is to record the hub's *resolved* effect in each entry, as "insert after <resolved left neighbour id>" in Weidner's sense, so that replay is unambiguous. The second is to make one sequence-CRDT semantics the log's definition from the start and treat the editors as views. The second conflicts with replaying into native CRDTs that make their own tie decisions. A related point: each entry should record the parents **the editor actually knew**, not the hub head, or the later merge loses the concurrency information it needs *(researchers' inference)*. Acceptance item 4 ("rebuild the document from the log alone") only tests the right thing if it rebuilds from entries carrying resolved left neighbours, and does not re-run either library's tie-break *(report inference)*.

## The operation algebra, row by row

### Text: solved, with a choice of semantics

Sequence CRDTs for text are mature. crdt.el uses Logoot-split, Yjs uses YATA, and Fugue/FugueMax and Eg-walker are the current published state of the art, with stronger non-interleaving guarantees ([arXiv 2305.00583](https://arxiv.org/abs/2305.00583); [arXiv 2409.14252](https://arxiv.org/html/2409.14252v1)). Logoot-split has no tombstones: deleted characters are removed from the buffer ([crdt-0.3.5 source](https://elpa.gnu.org/packages/crdt-0.3.5.tar)). So an id anchor pointing at a deleted Emacs character has nothing to resolve against on the Emacs side, and the hub has to keep the tombstone in its own log *(report inference)*.

### Spans and provenance: Peritext and Etherpad are solved; crdt.el is a poor carrier

Peritext anchors each mark end to the before or after gap of a specific character id. The choice of gap decides whether text typed at the boundary joins the span. Conflicting exclusive marks resolve by Lamport-timestamp last-writer-wins, comments are non-exclusive marks, and tombstones keep anchors alive after deletion ([Peritext essay](https://www.inkandswitch.com/peritext/)). Automerge (`mark` with `expand: before|after|both|none`) and Loro (`configTextStyle`, built on Peritext plus Fugue) ship it ([automerge mark API](https://automerge.org/automerge/api-docs/js/functions/mark.html); [loro-docs](https://github.com/loro-dev/loro-docs/blob/main/pages/docs/tutorial/text.mdx)). The researchers recommend that the mission state the gap side at each end of each span type explicitly. Notes, holes and scopes would normally use `expand: none` *(researchers' inference)*.

Etherpad confirms the mission's precedent. Authorship is an ordinary `(author, id)` attribute, interned in a pool and carried run-length in changesets and in the document's attribution string ([easysync-notes.txt](https://github.com/ether/etherpad-lite/blob/develop/doc/public/easysync/easysync-notes.txt)). The server rejects any `+` op whose `author` attribute is not the session's own author, and lets `=` ops restore an author already in the pool ([PadMessageHandler.ts](https://github.com/ether/etherpad-lite/blob/develop/src/node/handler/PadMessageHandler.ts)). Etherpad also shows the cost of keeping authorship in the content: "Clear authorship colours" rewrites the attribute, so provenance can be erased by editing ([ace2_inner.ts](https://github.com/ether/etherpad-lite/blob/develop/src/static/js/ace2_inner.ts)). The researchers suggest copying the server-side author check *(researchers' inference)*.

Yjs v14 takes the opposite approach. Attribution lives outside the content, in run-length-encoded `IdMap`s from id ranges to attribute sets, and is rendered through pluggable Renderers (`AttributionsRenderer`, `DiffRenderer`, `TwosetRenderer`). Suggestion mode works as a separate document diffed against the base ([yjs attributing-content.md](https://github.com/yjs/yjs/blob/main/attributing-content.md); [renderer.md](https://github.com/yjs/yjs/blob/main/renderer.md)). y-prosemirror v2 treats attribution marks as "presentation, not content", strips them before writing back, and warns that a non-deterministic mapper loops forever ([ATTRIBUTION.md](https://github.com/yjs/y-prosemirror/blob/main/ATTRIBUTION.md)). This matches the mission's provenance kinds better than formatting attributes do. "Kept" and "accepted" are events on existing ids, which fit as further IdMap layers and do not fit as attributes fixed at insert time *(researchers' inference)*. But **v14 is still a release candidate (rc.30, 2026-11-14), and its attribution API was renamed in a breaking change as late as 2026-06-16** ([yjs releases](https://github.com/yjs/yjs/releases); [commit history](https://github.com/yjs/yjs/commits/main/attributing-content.md)).

The mission's design point 2 relies on `crdt--enabled-text-properties` to carry provenance in Emacs. The notes show where that breaks. The variable defaults to `'(crdt-author)`. Enabled properties travel inside the `#("text" start end (prop value))` content of `insert` and `sync`, and **a change to an enabled property alone is sent as a delete of the range plus a re-insert with fresh ids** (the source still says `;; todo: track properties`) ([crdt-0.3.5 source](https://elpa.gnu.org/packages/crdt-0.3.5.tar), lines 1450-1495). On receipt, `crdt-author` is **overwritten with the message's user-id** (line 1349). It follows that two users changing a property on overlapping text at the same time produce **two copies of the text**, and an edit concurrent with a property change can be lost. The researchers did not reproduce either *(researchers' inference)*. Their recommendation: keep annotations as hub-side anchored ranges, and show them in Emacs through a custom **overlay species** (already id-anchored, last-writer-wins in server order) or a separate channel *(researchers' inference)*. A further point follows from the overwrite at line 1349. To get each author's colour on text the hub replays into Emacs, the hub has to send each replayed `insert` under a user-id that stands for the original author: a pseudo-user per browser author, announced with `contact`. If it sends everything as the hub, everything turns the hub's colour *(report inference; not tested)*. Insert-time provenance (author, source) can still ride in text properties, because it is fixed when the text is inserted. What should not ride there is anything that changes after insertion, such as kept, accepted, layer or notes *(report inference)*.

The incubator already anchors text by its words and context (DERIVE-2 §11). The notes treat the two anchor families as complementary. **Id anchors** (Yjs `RelativePosition`, Automerge cursors, Loro `Cursor`) are exact under concurrency but break across imports and copy/paste. **Quote anchors** (the W3C TextQuoteSelector with exact, prefix and suffix; Hypothes.is fuzzy anchoring with 32-character context) survive moves and re-imports, but can mis-attach ([W3C Web Annotation Data Model](https://www.w3.org/TR/annotation-model/); [Hypothes.is Fuzzy Anchoring](https://web.hypothes.is/blog/fuzzy-anchoring/)). Yjs collapses a position on deleted text to the deletion point ([RelativePosition.js](https://github.com/yjs/yjs/blob/v13.6.33/src/utils/RelativePosition.js)), while Automerge resolves toward one side ([getCursor](https://automerge.org/automerge/api-docs/js/functions/getCursor.html)). The researchers recommend the id anchor as primary, with a quote selector and a revision stamp stored beside it as fallback and drift check, and an explicit orphan state for spans whose two ends both land on tombstones *(researchers' inference)*.

### Nodes and hyperedges: solved for grow-only, with one caveat

Grow-only and two-phase sets of vertices and edges are CRDTs. Shapiro et al. (2011) work through the addEdge-versus-removeVertex conflict and the 2P2P-Graph ([INRIA RR-7506](https://www.csa.iisc.ac.in/~raghavan/CleanedPods2021/crdt-shapiro-2011-techreport.pdf)). With immutable nodes and hyperedges, the mission's "no conflicts" claim holds for adding. The caveat is referential integrity: a hyperedge that names a node from another replica's log must not be applied before that node exists. The 2P2P-Graph resolves this with causal delivery, and the OR-Set graph in the verification literature keeps the invariant explicitly ([arXiv 1905.05684](https://arxiv.org/pdf/1905.05684)). With the hub delivering in order this holds for free; after decentralisation it needs the causal parents in the log *(report inference)*.

### Derivation-tree versions: matches published prose version control

Upwelling (Ink & Switch, 2023) uses private draft layers that stack and rebase onto main ([Upwelling](https://www.inkandswitch.com/project/upwelling/)). Patchwork (2024) found branching only from main "occasionally proven insufficient", and found that users struggle to see how branches relate ([Patchwork notebook](https://www.inkandswitch.com/patchwork/notebook/2024-version-control/)). Pijul keeps conflicts as first-class states in an append-only graph and resolves them with a further change ([Pijul theory](https://pijul.org/manual/theory.html)). Mimram and Di Giusto model merge as a pushout and conflicts as a free cocompletion ([arXiv 1311.3903](https://arxiv.org/abs/1311.3903)). The mission's rule, "a later attributed act merges, by a person's judgement", is the Pijul approach, and its forks-from-a-layer are the general form of what Patchwork's users asked for. On the Patchwork evidence, the remaining cost is in showing users how the branches relate, not in the merge rule *(researchers' inference)*.

### Move or regroup: trees are solved, ranges and graphs are open

Tree move is solved and machine-checked. Kleppmann, Mulligan, Gomes and Beresford (IEEE TPDS 33(7), 2021) use a Lamport-ordered log with undo-do-redo, skip any move that would make a node its own ancestor, and prove in Isabelle/HOL that the result is acyclic with one parent per node ([paper](https://martin.kleppmann.com/papers/move-op.pdf); [trvedata/move-op](https://github.com/trvedata/move-op)). The cost is throughput under concurrency: **5,700 ops/s for the handwritten CRDT against 22,000 ops/s for a leader-based design**, which also checks cycles but never undoes ([paper](https://martin.kleppmann.com/papers/move-op.pdf)). Loro ships a movable tree on this algorithm ([Loro tree](https://www.loro.dev/docs/tutorial/tree)). Evan Wallace's alternative keeps each node's parent history and derives the tree deterministically, and he calls it "tricky to reason about" ([madebyevan.com](https://madebyevan.com/algos/crdt-mutable-tree-hierarchy/)). Single-element list move is solved (Kleppmann PaPoC 2020; Loro MovableList). **Moving a range of text, such as a paragraph, is named an open problem in the paper itself** ([Kleppmann PaPoC 2020](https://martin.kleppmann.com/2020/04/27/papoc-list-move.html)). Yjs has no move, and a concurrent delete+insert duplicates the element ([Yjs forum](https://discuss.yjs.dev/t/moving-elements-in-lists/92)). JSON-tree move has a published algorithm (Da & Kleppmann, PaPoC 2024: "largest ID wins", delete as a move to trash), but only as a prototype outside the Rust Automerge library ([arXiv 2311.14007](https://arxiv.org/html/2311.14007v1)).

For graphs, Shapiro et al. state that keeping a tree or DAG shape "cannot be done by a CRDT" without synchronisation. The exception is an add-only monotonic DAG, whose new edges follow existing paths ([INRIA RR-7506](https://www.csa.iisc.ac.in/~raghavan/CleanedPods2021/crdt-shapiro-2011-techreport.pdf)). The researchers found **no published CRDT for move or regroup in a hypergraph, and none for DAG-preserving reparenting of multi-parent nodes**, and note the search was short. Their analysis of the mission's candidate rule, move as new version plus supersede, is as follows *(researchers' inference)*. The rule is acyclic by construction, provided supersede edges always point from a freshly created node to existing ones, by the same argument as Shapiro's `addBetween`. Its anomaly is a fork rather than a cycle: two concurrent supersedes of one version give two sibling successors. That is the TPDS "duplication" outcome, but the mission already sends it to a person's judgement, so nothing is silently dropped. The rule leaves one problem open: **an annotation made on version v while v is being superseded by v′ stays on v**, and the notes found no published algorithm that forward-ports it. A regroup that rewires *existing* nodes under an acyclicity requirement falls under Shapiro's impossibility result. It needs a total order (log replay), a per-node history with a derived view (Wallace; silk-graph's quarantine of invalid entries, [silk-graph](https://docs.rs/crate/silk-graph/latest)), or the hub as coordinator. One point the mission can use now: while there is a hub, the hub can reject cycle-closing regroups the way Figma's server does ([Wallace on Figma](https://madebyevan.com/figma/how-figmas-multiplayer-technology-works/), primary text not fetched). That rule does not survive decentralisation, so the log should record rejected claims rather than drop them *(report inference)*.

## Messages the hub must handle (acceptance item 1)

### crdt.el side, with the hub as server

Transport is plain TCP (default port 6530). Messages are printed Emacs Lisp lists written back to back, with no length prefix or delimiter. The receiver loops `read` over a buffer and keeps any incomplete tail ([crdt-0.3.5 source](https://elpa.gnu.org/packages/crdt-0.3.5.tar), lines 2003-2054). The hub therefore needs a resumable reader and printer for a subset of Emacs Lisp: lists, dotted pairs, symbols, fixnums, `nil`/`t`, multibyte UTF-8 strings, **unibyte id strings with `\NNN` octal escapes and raw control and NUL bytes**, and `#("str" start end plist)` propertized strings. Ids must be kept as byte arrays *(researchers' inference, from their local experiment)*. There are 22 message types. **An unknown message type, or unreadable syntax, disconnects the peer**, so the hub cannot add message types of its own ([crdt-0.3.5 source](https://elpa.gnu.org/packages/crdt-0.3.5.tar)).

| Message | Direction | Body | What the hub does |
|---|---|---|---|
| `hello` | C→S | `(protocol-version &optional response)` | Check the version: reject only versions lower than its own with `(error nil version "0.3.0")`; verify the HMAC response |
| `challenge` | S→C | `(salt)` (32 random bytes) | Send when a password is set; expect HMAC-SHA1(password, salt) |
| `login` | S→C | `(user-id)` | Assign user ids from 1 (the hub is 0) |
| `add` / `remove` | S→C | `buffer-name ...` | Announce or withdraw shared buffers (one per answer/layer) |
| `contact` | both | `(user-id slot value)`, slot ∈ name, host, service, focus | Relay; reject a client claiming another's id; announce pseudo-users for browser authors |
| `leave` | both | `(user-id)` | Drop the connection; synthesise `leave` plus a clearing `cursor` when a socket drops |
| `fcap` | S→C | `(symbol nonce in-states out-states . interactive-form)` | Advertise **only** `crdt-get-write-access` (and `crdt-get-buffer-create` if Emacs users may add buffers) |
| `get` | C→S | `(buffer-name)` | Reply with the sync batch; also the client's error-recovery path |
| `sync` | S→C | `(buffer-name . ((CONTENT ID EOB) ...))` | Full content as id blocks in document order |
| `ready` | S→C, also C→S | `(buffer-name major-mode)` | End a sync batch; accept from a client sharing a buffer |
| `insert` | both, relayed | `(buffer-name user-id crdt-id position-hint content)` | Apply by id (the hint only speeds the search), relay, translate to Yjs, log |
| `delete` | both, relayed | `(buffer-name user-id position-hint . ((LENGTH ID) ...))` | Same |
| `cursor` | both, relayed | `(buffer-name user-id point-hint point-id mark-hint mark-id)` | Relay; map to and from Yjs awareness |
| `overlay-add` / `-remove` | both, relayed | keyed by `(user-id . logical-clock)`, id-anchored ends | Relay; candidate carrier for hub-side spans |
| `overlay-move` / `-put` | both, **echoed to sender** | as above | Relay to all, including the sender |
| `funcall` / `return` | C→S / reply | `(uid clock spawn-uid state-list nonce fcap . args)` / `(uid clock state-list success-p . values)` | Answer `crdt-get-write-access` with a site id; answer unknown calls with failure promptly, because **the Emacs caller blocks with no timeout** |
| `var`, `process`, `process-mark` | various | buffer-local variable and comint sync | Accept and relay or ignore; never leave unhandled |
| `error` | S→C | `(buffer-name sym . data)` or `(nil version V)` | Send to make a client resync a buffer |

Sources for the table: [crdt-0.3.5 source](https://elpa.gnu.org/packages/crdt-0.3.5.tar) and [HACKING.org](https://code.librehq.com/willforan/crdt.el/-/raw/38476dac4630b18bbf3199ee6ab26a9e95c96fc0/HACKING.org). The minimal set for a text-only hub is `hello`/`challenge`, `login`, `add`, `contact`, the write-access `fcap`, `get`→`sync`+`ready`+`cursor`, `funcall`→`return`, and apply-and-relay for `insert`, `delete`, `cursor`, `contact` and `leave`. Every other type must still be accepted, because an unknown type disconnects the peer *(researchers' inference)*. Three more consequences follow. Withholding the write-access fcap makes an Emacs client read-only, which gives per-user permissions. The default session also grants xscheme, comint and xref fcaps, which the hub must not advertise, because clients forward those commands to the server and block waiting for the answer. And the password check is HMAC-SHA1 over a cleartext stream with no native TLS listener (stunnel is "experimental"), so the Emacs edge belongs behind TLS or an SSH tunnel *(researchers' inference)*. The mission's planned Caddy basic-auth realm covers HTTP only and does not protect this raw TCP port *(report inference)*.

### Yjs side

| Message | Bytes | What the hub does |
|---|---|---|
| SyncStep1 | `00 00 varBuffer(stateVector)` | Client sends on connect; the hub replies with SyncStep2, then sends its own SyncStep1 |
| SyncStep2 | `00 01 varBuffer(update)` | Diff against the received state vector, both directions; reject from read-only peers |
| Update | `00 02 varBuffer(update)` | Apply under the hub lock with a per-connection origin, translate to crdt.el, log; reject from read-only peers |
| Awareness | `01 varUint(n) {clientID clock json(state)}*` | Apply when the clock increases; `null` = offline; expire after 30 s; map to crdt.el `cursor`/`contact`; **unauthenticated at this layer** |
| Auth (2), queryAwareness (3) | reserved / not in the spec | Present in y-protocols source and y-websocket; not specified |

Sources: [y-protocols PROTOCOL.md](https://github.com/yjs/y-protocols/blob/master/PROTOCOL.md). y-websocket and Hocuspocus clients speak the **V1** update format inside these messages. V2 is useful only for compact storage, converted at the boundary *(researchers' inference)*. The V1/V2 *update* byte encoding has no standalone spec; the reference is the yjs and yrs source. That is why the hub embeds an engine for it rather than writing one. If the Yjs edge is a Hocuspocus sidecar, the hub also consumes its hooks: `onChange` gives update bytes, a structured `transactionOrigin` and auth `context`; `onAuthenticate` returns identity; `beforeHandleMessage` can reject ([Hocuspocus hooks](https://tiptap.dev/docs/hocuspocus/server/hooks)). Origins never travel inside update bytes, so durable authorship needs a server-side clientID→identity table, filled at authentication time *(researchers' inference)*. For checkpointing and history, the hub replica runs with **`gc: false`** ([Yjs README](https://raw.githubusercontent.com/yjs/yjs/v13.6.33/README.md)).

## One merge engine with thin clients, against two bound CRDTs

The notes surfaced an alternative the mission does not consider. **Ethersync/Teamtype** keeps each file in an Automerge CRDT inside a daemon. Editors are thin clients on an LSP-like JSON-RPC protocol, with an editor revision and a daemon revision per file. A daemon edit computed against a stale editor revision is ignored, and the daemon later sends a transformed one. The protocol is a "one-sided operational transform", built to "offload as much work as possible into the daemon" ([FOSDEM 2025 slides](https://fosdem.org/2025/events/attachments/fosdem-2025-4890-ethersync-real-time-collaboration-in-your-text-editor-/slides/237972/ethersync_e3Ip0mj.pdf); [Teamtype docs](https://teamtype.github.io/teamtype/print.html)). Official Neovim and VS Code plugins exist, and at FOSDEM 2025 an Emacs plugin was listed as community work in progress. **braid-text** merges on the server with diamond-types (Gentle's Eg-walker implementation). Its Simpleton clients carry "zero history overhead" and can be about 50 lines of code ([braid-text](https://github.com/braid-org/braid-text); [Braid-HTTP draft](https://datatracker.ietf.org/doc/html/draft-toomim-httpbis-braid-http-04)). Weidner's server reconciliation has the same shape: insert-after-id ops, server order as truth, clients that undo and redo pending ops ([mattweidner.com](https://mattweidner.com/2025/05/21/text-without-crdts.html)).

The researchers compare the two *(researchers' inference)*. A single engine at the hub, with Emacs and the web client as thin OT- or Simpleton-style clients, removes the cross-CRDT tie-order problem, the two-way id maps, and the risk that the log's semantics differ from what users saw. If that engine is Eg-walker, it is also the decentralisation story the mission wants. What it gives up is crdt.el's and Yjs's own peer sync and their existing editor bindings. Two further points sharpen the comparison *(report inference)*. First, neither side has a ready editor binding to the hub: the bound-CRDT design still needs a code-server extension, because no VS Code Yjs binding exists, and a crdt.el-speaking hub, which nobody has built. The thin-client design needs an Emacs client (perhaps the in-progress Teamtype one) and a VS Code client (Teamtype's exists). So the bound design saves less editor work than it first appears to. Second, the thin-client design is a better fit for provenance. One engine at the hub can stamp `murch:412`-style run ids at insert and keep attribution as an IdMap-style layer. The bound design has to infer authorship from native ids that the hub owns on one side. A mixed version is also possible: keep Yjs for the browser, where the binding ecosystem is strong, and make Emacs a thin client of the hub instead of a crdt.el peer. That removes the crdt.el text-property problem described above. The notes did not research this mixed option.

For acceptance item 5, a concurrent-move test should build the exact cases the literature names *(report inference)*. Two replicas supersede the same version at once: expect two sibling successors, not a lost move. Two regroups that would close a cycle (Shapiro's addEdge(u,v) ∥ addEdge(v,u)): expect the hub to reject one and the log to keep both claims. An annotation made on v concurrently with v being superseded: the test should show where it ends up, since no published rule decides this.

## Conclusion

The part of the mission that most needs a decision before building is not the hub's message handling, which is now catalogued, but the **meaning of the log**. If each entry records the editor's real parents and the hub's resolved placement, the log is an Eg-walker graph that can be replayed exactly and merged without a hub later. If it records only the native ops, the history depends on two libraries' tie-breaks that a future hub-less merge will not reproduce. The same decision settles where provenance lives. The notes point toward the Yjs v14 approach, attribution as id-keyed layers outside the text, and away from crdt.el text properties, which can only safely carry facts fixed at insert time.

The thin-client alternative deserves a short spike before plan step 2 commits to crdt.el. On the side-by-side above, it removes problems the bound design has to solve (id maps, tie order, property re-inserts) and saves little editor work by comparison, since a code-server binding and a crdt.el-speaking server have to be written either way. Move and regroup are the one place where the research confirms the mission's "open" label. The new-version-plus-supersede rule is acyclic and does not lose moves silently. What remains unsolved, and not addressed anywhere in the published work found, is forwarding concurrent annotations from a superseded version.
